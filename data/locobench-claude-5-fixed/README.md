# locobench-claude-5-fixed

Two CONFLICT families (10 items) generated by `claude-opus-5` through the IBM LiteLLM
gateway, using the generator **after** the per-rung gold-relation fix.

Regenerate with:

```
OPENAI_API_KEY=$ANTHROPIC_AUTH_TOKEN \
locobench-generate --config configs/locobench_claude.json \
    --out data/locobench-claude-5-fixed \
    --dataset-name locobench-claude-5-fixed \
    --n-families 2 --limit 2
```

## Why this exists alongside `data/locobench-claude-5`

`data/locobench-claude-5` was generated before the fix. There, every rung of a family
carried the **base plan's** relation list: `pipeline.py` perturbed each rung's *text* but
re-attached the same gold edges to all five items, and every P5 call was passed the
hardcoded target `r000`. Consequences, both visible by comparing the two directories:

| | `locobench-claude-5` (pre-fix) | `locobench-claude-5-fixed` |
|---|---|---|
| relations per item | uniformly 10 | 8-11, varying by rung |
| distinct edge sets per family | 1 of 5 rungs | 5 of 5 rungs |
| adjacent rungs with identical edge sets | all 4 pairs | none |
| ordering constraints satisfied, gold arm, per family | 1 / 14 | 11 / 14 |
| ordering constraints satisfied, gold arm, both families | 2 / 28 | 22 / 28 |

Everything else is held constant: same generator, same two canonical topics
(Anthropology, Archaeology), 16 atoms per item, and five distinct response texts per
family in both.

Because the pre-fix corpus's gold relations were constant within a family, every LCS
readout was constant too, so the strict-increase ordering constraints in `families.json`
could not hold by construction — the ladder was untestable from gold alone. Here each
rung's labels describe the response that ships with them, so those constraints are a real
test of the readouts.

## What the fix changed in the generator

* `perturb.apply_calls` — applies a rung's operator calls to the base gold edge set, so a
  rung's relations are the base relations plus its own perturbations. Derived fields
  (coupling, directedness, ordering-only, exhaustiveness) are re-derived from the sense via
  `taxonomy_bridge`, so a transformed edge cannot contradict `lcs.taxonomy.COMPILE`.
* `perturb.plan_targets` — assigns each call a distinct eligible edge, so a rung composing
  two `drop_relation` calls drops two different edges.
* An **adjacency gate** in `pipeline.py` — a family is rejected when two *adjacent* rungs
  build the same edge set while the higher rung's calls claim a change. Adjacency, not
  parentage: every CONFLICT rung's declared parent is the base, so a parent-only comparison
  passes a rung that duplicates the rung immediately below it. `EDGE_INVARIANT_CALLS`
  exempts `shuffle_order` and `ordering_only`, which are factor-invariant by design and are
  what the ORDER and CONTROL ladders exist to check.

A CONFLICT ladder needs **three unresolved conflict edges** in its plan (one for
`add_resolution`, two for the drops). A plan with fewer is now rejected rather than
silently emitting a rung that duplicates its neighbour.

## Evaluation

LCS scores for this dataset: `results/locobench_claude_5_fixed_lcs/report.pdf`
(the pre-fix run is kept at `results/locobench_claude_5_lcs/` for comparison).

```
locobench-lcs-eval --data-dir data/locobench-claude-5-fixed \
    --out-dir results/locobench_claude_5_fixed_lcs \
    --merlin-path /path/to/merlin
```
